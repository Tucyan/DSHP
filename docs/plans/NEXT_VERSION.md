# 下个版本需求与静默回复排查

记录日期：2026-09-15。需求已实现并进入发布版本；部署结果记录在 `progress.md` 和运维文档中。

## 1. 前台心跳唤醒 main agent

- 定时触发固定主会话的一轮执行，移除独立联系决策器在此路径上的职责。
- main agent 自行检查目标、待办与上下文，允许使用工具推进工作，无事可做时安静结束。
- 通过 send_message 按需联系用户；区分用户轮次与心跳轮次。
- 忙碌时排队或合并心跳，避免打断用户及重复执行。
- 将主动联系策略应用于发送环节，保留免打扰、冷却、每日上限及持久化去重。

## 2. 用户消息静默问题（优先）

### 生产证据

服务器版本 dc3a9c9，服务 active，NRestarts=0。只读检查 trace.jsonl 与完整多帧压缩会话事件；未调用模型、未发送 QQ 消息、未改变服务。

- 2026-09-15 15:28:30–15:28:42（UTC+8），turn 24：用户请求每天 20:00 检查 GitHub commit。模型调用 bash、schedule_create、personal_memory_apply，最后输出普通 assistant 文本“已设好每晚20:00检查，今天20:00开始”。没有 send_message 调用，没有 outbound 记录，turn completed。本记录不据此断言定时任务配置正确。
- 16:08:54–16:09:03，turn 25：用户要求测试多次发送。存在三次 send_message、三次持久化 message-sent 和 outbound sent；下一条用户消息确认收到三条。
- 16:09:19–16:09:21，turn 26：用户确认收到。模型输出普通 assistant 文本“太好了，以后提醒和进度可以分条发送”，没有工具发送或 outbound 记录，turn completed。
- turn 24 的实际 request/header 已包含完整 MESSAGE_DELIVERY_PROMPT，明确要求所有用户可见回复调用 send_message，且工具描述存在。不能归因为提示词未注入。

### 结论

已核实的两次静默是模型未使用发送工具，而不是 QQ 已发送但未收到。模型生成了回复；Host 刻意不转发普通 assistant 文本，并在 whenIdle 后直接将 inbound 标记 completed，没有要求用户轮次必须有可见回复。提示词服从性偏差与缺少运行时交付保障共同造成静默。

### 待实现方案与验收

- 用户轮次结束时核查交付状态，不能只依赖模型遵守 prompt。
- 优先考虑有界纠正一次让模型使用 send_message；仍未交付时采用明确的安全兜底。最终方案实施前确定，不能自动转发思考、内部工具输出或任意 assistant 文本。
- 区分零次调用、调用失败、投递结果未知、已成功发送但缺少最终答复；未知结果不得盲目重发。
- 保持已有多消息发送、继续执行与去重行为，避免重新引入重复回复。
- 增加每轮关联的发送次数、成功/未知状态、无回复原因等诊断信息，管理页能够区分模型未发送与传输失败。
- 心跳允许静默，普通用户请求默认需要可见回复；显式要求不回复等例外需定义。
- 测试普通文本但无发送、工具任务完成后未发送、发送失败/未知、已发送后的最终文本、用户轮次与心跳轮次差异。

## 3. 管理页编辑心跳提示词并热加载

- 支持前台心跳和后台心跳提示词编辑、持久化保存及热加载。
- 前台字段编辑的是 main agent 被心跳唤醒时的指令。
- 后台字段编辑的是维护任务指令；Dream/记忆整理提示词不在本次明确需求中。
- 每轮使用固定提示词快照；保存后下一轮生效，避免进行中的任务混用版本。
- 沿用鉴权、CSRF、版本冲突检查和审计机制。
- 可编辑业务指令与不可编辑的工具权限、动作校验、联系策略边界分离。
